# ร่างโครงสร้างฐานข้อมูลสำหรับตรวจ ก่อนเริ่มพัฒนาเว็บ

วันที่ 27 กันยายน 2026 · สถานะ: **รอผู้ใช้ตรวจและอนุมัติ**

แหล่งอ้างอิง: `ER-จารย์จ๊อบตรวจแล้ว.pdf` จำนวน 5 หน้า อ่านตัวอย่างหน้า 1–3 ประกอบ ER หน้า 4 และรายการ PK/FK หน้า 5

ยังไม่ได้เชื่อมต่อฐานข้อมูล ไม่ได้รัน SQL และไม่ได้เริ่มสร้าง Client/Server ชุดใหม่ ไฟล์ `schema-oracle-DRAFT.sql` เป็นร่างให้ตรวจเท่านั้น ไม่ได้บรรจุข้อมูลล็อกอินฐานข้อมูล

## การแยกชื่อจากตารางงานเดิม

ปรับชื่อตารางทั้ง 13 ตารางให้ขึ้นต้น `BUS_` ตามข้อเสนอผู้ใช้ เช่น `BUS_DEPARTMENTS`, `BUS_EMPLOYEES`, `BUS_USERS` และ `BUS_BOOKINGS` พร้อมปรับชื่อ constraint และ index ให้ขึ้นต้น `BUS_` ด้วย เช่น `BUS_PK_EMPLOYEES`, `BUS_FK_EMP_DEPARTMENT` และ `BUS_IX_EMPLOYEE_DEPARTMENT`

ชื่อคอลัมน์ เช่น `employee_id` และ `department_id` คงเดิมได้ เพราะเป็นคอลัมน์ของคนละตาราง FK ทุกตัวในร่างนี้เชื่อมเฉพาะตารางชุด `BUS_` ไม่มีการอ้างอิงไปยังตารางเรียนเดิม เช่น `EMPLOYEE` หรือ `DEPARTMENT`

ภาพแสดง `DEPARTMENT` และ `EMPLOYEE` แบบเอกพจน์ ส่วนร่างก่อนหน้านี้ใช้ `departments` และ `employees` จึงยังไม่ใช่ชื่อเดียวกัน แต่รายการในภาพระบุว่า Tables (Filtered) จึงไม่ใช้ภาพนี้ยืนยันว่าทั้ง schema ไม่มีชื่อซ้ำ

ไฟล์ `check-bus-names.sql` มีเฉพาะ SELECT สำหรับตรวจชื่อ object และ constraint ที่ร่างนี้จะสร้าง ใน schema ของบัญชีที่ล็อกอินอยู่ ถ้าทั้งสองผลลัพธ์ไม่มีแถว แปลว่าไม่พบชื่อที่จะชนในขณะตรวจ หากมีผลลัพธ์ ให้ตรวจว่าคืออะไรหรือเลือก prefix ใหม่ก่อนสร้าง อย่าลบหรือเขียนทับงานเดิมเพื่อให้รันผ่าน

ยังไม่ได้รันแม้แต่คำสั่งตรวจชื่อกับฐานข้อมูลจริง และการปรับชื่อครั้งนี้ไม่ถือว่าผู้ใช้อนุมัติโครงสร้าง/Partial Key หรืออนุญาตให้สร้างตารางแล้ว

## งานที่เข้าใจตรงกัน

นำหน้าเว็บและพฤติกรรมจาก Figma Make เดิมมาใช้เป็น React Client ให้ใกล้เคียงของเดิมที่สุด สร้าง Server/API แยก แล้วให้ Server อ่านและเขียนฐานข้อมูลจริง เมื่อรัน Client และ Server สามารถเปิดเว็บบนเครื่องเพื่อเพิ่ม แก้ไข ลบ และเรียกดูข้อมูลได้

```mermaid
flowchart LR
  A[เว็บ React บน localhost] -->|เรียก API| B[Server]
  B -->|SQL และธุรกรรม| C[(ฐานข้อมูล Oracle)]
  C --> B --> A
```

ข้อมูลเชื่อมต่อฐานข้อมูลจะอยู่เฉพาะฝั่ง Server ไม่ใส่ใน React ที่ส่งไปยังเบราว์เซอร์ ส่วน Server จะเป็น Node/Express หรือ ASP.NET ต้องตรวจโปรเจกต์เดิมและชนิดที่เคยใช้ก่อน เพราะ React ใช้คู่กับทั้งสองแบบได้

## PK และ FK คืออะไร

- **PK (Primary Key)** คือค่าที่ระบุแถวหนึ่งได้แน่นอน ห้ามซ้ำและห้ามว่าง เช่น `BUS_EMPLOYEES.employee_id`
- **FK (Foreign Key)** คือค่าที่ต้องอ้างถึงแถวที่มีอยู่ในอีกตาราง เช่น `BUS_EMPLOYEES.department_id` ต้องมีใน `BUS_DEPARTMENTS.department_id`
- **PK คู่** ใช้สองคอลัมน์ประกอบกัน เช่น การจอง B001 ตั๋ว 01 กับการจอง B002 ตั๋ว 01 ถือว่าคนละตั๋ว
- **1:N** หมายถึงหนึ่งแถวฝั่งแรกมีได้หลายแถวฝั่งที่สอง เช่น แผนกหนึ่งมีพนักงานหลายคน

## ตารางและความสัมพันธ์ที่ถอดจาก ER

ใช้ชื่อภาษาอังกฤษใน SQL เพื่อให้เรียกจากโปรแกรมสะดวก มี 13 ตารางตาม ER หน้า 4–5

| ตารางใน ER | ชื่อตาราง SQL | PK | FK ไปตารางใด |
|---|---|---|---|
| แผนก | `BUS_DEPARTMENTS` | `department_id` | ไม่มี |
| ตำแหน่ง | `BUS_POSITIONS` | `position_id` | ไม่มี |
| หน้าจอ | `BUS_SCREENS` | `screen_id` | ไม่มี |
| พนักงาน | `BUS_EMPLOYEES` | `employee_id` | `department_id → BUS_DEPARTMENTS.department_id`; `position_id → BUS_POSITIONS.position_id` |
| สิทธิ์การเข้าถึง | `BUS_POSITION_PERMISSIONS` | `permission_id` | `position_id → BUS_POSITIONS.position_id`; `screen_id → BUS_SCREENS.screen_id` |
| จุดจอด | `BUS_STOPS` | `stop_id` | ไม่มี |
| เส้นทาง | `BUS_ROUTES` | `route_id` | ไม่มี |
| จุดจอดในเส้นทาง | `BUS_ROUTE_STOPS` | `route_stop_id` | `route_id → BUS_ROUTES.route_id`; `stop_id → BUS_STOPS.stop_id` |
| รถ | `BUS_VEHICLES` | `vehicle_id` | ไม่มี |
| รอบเวลาเดินรถ | `BUS_TRIP_ROUNDS` | `trip_id` | `route_id → BUS_ROUTES.route_id`; `driver_employee_id → BUS_EMPLOYEES.employee_id`; `vehicle_id → BUS_VEHICLES.vehicle_id` |
| ผู้ใช้งาน | `BUS_USERS` | `user_id` | ไม่มี |
| การจอง | `BUS_BOOKINGS` | `booking_id` | `trip_id → BUS_TRIP_ROUNDS.trip_id`; `user_id → BUS_USERS.user_id` |
| รายละเอียดการจอง | `BUS_BOOKING_DETAILS` | **ร่างเป็น `(booking_id, ticket_no)` รออนุมัติ** | การจอง, รอบรถ, รถ, จุดขึ้น และจุดลง ตามรายละเอียดด้านล่าง |

ตาราง `User` เปลี่ยนชื่อทางเทคนิคเป็น `BUS_USERS` เพื่อเลี่ยงชื่อ `USER` ใน SQL ไม่ใช่การเพิ่มตารางอีกตัว

## คอลัมน์ของแต่ละตาราง

ชนิดและความยาวข้อมูลเป็นข้อเสนอสำหรับร่าง ไม่ได้มีระบุครบใน ER ใช้รหัสแบบ `VARCHAR2` เพื่อเก็บ `01` หรือ `E001` ได้โดยศูนย์ด้านหน้าไม่หาย ใช้ `NVARCHAR2` กับชื่อภาษาไทย และใช้ `NUMBER(1)` ค่า 0/1 แทน Boolean เพื่อลดข้อจำกัดจากรุ่น Oracle ที่ยังไม่ทราบ

| ตาราง | คอลัมน์ทั้งหมด |
|---|---|
| `BUS_DEPARTMENTS` | `department_id`, `department_name` |
| `BUS_POSITIONS` | `position_id`, `position_name` |
| `BUS_SCREENS` | `screen_id`, `screen_name` |
| `BUS_EMPLOYEES` | `employee_id`, `full_name`, `username`, `password_hash`, `phone`, `email`, `department_id`, `position_id` |
| `BUS_POSITION_PERMISSIONS` | `permission_id`, `position_id`, `screen_id`, `can_view`, `can_modify` |
| `BUS_STOPS` | `stop_id`, `stop_name` |
| `BUS_ROUTES` | `route_id`, `route_name`, `total_minutes` |
| `BUS_ROUTE_STOPS` | `route_stop_id`, `route_id`, `stop_id`, `stop_sequence`, `minutes_from_prev` |
| `BUS_VEHICLES` | `vehicle_id`, `license_plate`, `vehicle_type`, `seat_count` |
| `BUS_TRIP_ROUNDS` | `trip_id`, `route_id`, `driver_employee_id`, `vehicle_id`, `departure_at`, `status` |
| `BUS_USERS` | `user_id`, `full_name`, `username`, `password_hash`, `phone`, `user_type` |
| `BUS_BOOKINGS` | `booking_id`, `trip_id`, `user_id`, `booked_at`, `status` |
| `BUS_BOOKING_DETAILS` | `booking_id`, `ticket_no`, `trip_id`, `vehicle_id`, `pickup_route_stop_id`, `dropoff_route_stop_id`, `seat_number`, `travel_at`, `checked_in_at`, `status`, `qr_token` |

`password_hash` ใช้เก็บค่าที่ผ่านการ hash จาก Server แทนรหัสผ่านจริง เครื่องหมาย `********` เป็นเพียงการแสดงในหน้าจอ ไม่ใช่ค่าที่ต้องบันทึกในฐานข้อมูล

`departure_at` รวมวันที่และเวลาออกรถใน ER ไว้ใน `TIMESTAMP` เดียว ส่วน `travel_at` รวมวันที่และเวลาเดินทางบนตั๋ว หน้าจอสามารถแยกแสดงวันที่กับเวลาได้เหมือนเดิม ร่างตีความ `travel_at` ว่าเวลาไปรับที่จุดขึ้นของผู้โดยสาร ซึ่งอาจต่างจากเวลาออกจากต้นทาง **ต้องให้ผู้ใช้ตรวจความหมายนี้ก่อน**

`checked_in_at` ว่างได้เมื่อยังไม่ได้เช็กอิน ส่วน `qr_token` เป็นข้อความ/รหัสเฉพาะตั๋วที่ใช้สร้าง QR ไม่ต้องเก็บรูป QR ลงตาราง

## จุดสำคัญ: Booking กับ Booking Details

ร่างใช้ **หนึ่งการจองอยู่ในหนึ่งรอบรถและมีตั๋วหลายใบได้** ตัวอย่าง จอง B001 ในรอบ T001 ให้ 2 ที่นั่ง จะมี `BUS_BOOKINGS` 1 แถว และ `BUS_BOOKING_DETAILS` 2 แถว:

| booking_id | ticket_no | trip_id | seat_number |
|---|---|---|---|
| B001 | 01 | T001 | A1 |
| B001 | 02 | T001 | A2 |

ถ้าตะกร้ามีหลายรอบรถ การกดยืนยันทั้งหมดจะสร้างหลาย `BUS_BOOKINGS` ภายในธุรกรรมเดียวกัน ไม่ยัดหลายรอบลงใน `BUS_BOOKINGS` แถวเดียว เพราะหน้า 5 กำหนด FK รหัสเที่ยวรถไว้ใน `Booking`

หน้า 3–4 เขียนรหัสตั๋วเป็น **Partial Key** และวาดรายละเอียดการจองเป็น weak entity แต่หน้า 5 ไม่แจกแจง PK คู่หรือ FK กลับไป Booking/รอบรถครบทุกตัว ร่างจึงเสนอ PK คู่ดังข้างต้น ไม่ถือว่าเป็นข้อสรุปที่อนุมัติแล้ว หากอาจารย์ต้องการรหัสตั๋วไม่ซ้ำทั้งระบบ สามารถเปลี่ยนเป็น `ticket_id` PK เดี่ยว โดยยังคง `booking_id` FK ได้

FK จริงของ `BUS_BOOKING_DETAILS` ใน SQL ร่าง:

1. `(booking_id, trip_id) → BUS_BOOKINGS(booking_id, trip_id)` ให้ตั๋วอยู่ในรอบเดียวกับใบจอง
2. `(trip_id, vehicle_id) → BUS_TRIP_ROUNDS(trip_id, vehicle_id)` ให้ตั๋วใช้รถที่กำหนดในรอบนั้น
3. `vehicle_id → BUS_VEHICLES.vehicle_id` ตามรายการ FK รถใน ER หน้า 5
4. `pickup_route_stop_id → BUS_ROUTE_STOPS.route_stop_id` จุดขึ้น
5. `dropoff_route_stop_id → BUS_ROUTE_STOPS.route_stop_id` จุดลง

FK คู่สองข้อแรกเป็นข้อเสนอเพิ่มความแน่นอนของข้อมูล โดยใช้ UNIQUE คู่ในตารางแม่รองรับ ไม่ได้เปลี่ยน PK หลักของ Booking หรือ Trip Round

## จุดจอดชื่อซ้ำต้องแยกให้ออก

ER หน้า 4 ลากเส้นขึ้น/ลงจากรายละเอียดการจองไปที่ **จุดจอดในเส้นทาง** จึงอ้าง `BUS_ROUTE_STOPS` แทน `BUS_STOPS` โดยตรง ตัวอย่างโลตัสหนองจอกขาไปและขากลับใช้ `stop_id` เดียวกัน แต่มี `route_stop_id` และ `stop_sequence` คนละค่า

SQL กำหนด UNIQUE `(route_id, stop_sequence)` เพื่อไม่ให้ลำดับชน แต่ไม่ห้าม `(route_id, stop_id)` ซ้ำ ทำให้เพิ่มจุดเดิมหลายตำแหน่งในเส้นทางเดียวกันได้

## กฎที่เสนอเพิ่มใน SQL ซึ่งต้องตรวจด้วย

- Username ไม่ซ้ำภายในตารางพนักงาน และไม่ซ้ำภายในตารางผู้ใช้ แต่ **ยังไม่ได้ห้ามชื่อซ้ำข้ามสองตาราง** ต้องตกลงวิธีแยกประเภทบัญชีตอนล็อกอินก่อน
- หนึ่งตำแหน่งมีสิทธิ์ต่อหนึ่งหน้าจอได้เพียงแถวเดียว; ค่า `can_view` และ `can_modify` เป็น 0/1
- ทะเบียนรถและ QR token ไม่ซ้ำ; จำนวนที่นั่งเป็นบวก; นาทีเดินทางไม่ติดลบ
- Seat number เป็นข้อความ เช่น `A1`, `C2` ตามตัวอย่างใน ER ไม่บังคับเป็นเลขอย่างเดียว
- เสนอ unique index กันที่นั่งซ้ำ **ตลอดทั้งรอบรถ** สำหรับตั๋วที่ยังไม่ยกเลิก/ไม่เป็น no-show ถ้าต้องการขายที่นั่งเดียวกันซ้ำในช่วงเส้นทางที่ไม่ทับกัน ต้องเปลี่ยนกติกานี้
- การยกเลิกเป็นการเปลี่ยนสถานะ เก็บตั๋วเดิมไว้สำหรับหน้าประวัติ ไม่ใช่ DELETE แถวนั้น
- FK ไม่มี `ON DELETE CASCADE`: ข้อมูลแม่ที่มีรายการอ้างอิงจะไม่ถูกลบพร้อมประวัติโดยอัตโนมัติ ต้องกำหนดข้อความตอบกลับหรือการปิดใช้งานใน Server
- สถานะภาษาอังกฤษใน SQL เป็นค่าที่เสนอให้โปรแกรมใช้งาน ต้องแปลงเป็นภาษาไทยในหน้าจอ และกำหนดการเปลี่ยนสถานะให้ตรงกันระหว่าง Booking กับตั๋ว
- รหัสทุกตารางให้ Server ส่งค่า ไม่ใช้ตัวนับจากจำนวนแถว เพราะอาจชนเมื่อหลายคนเพิ่มพร้อมกัน รูปแบบรหัสจริงยังไม่กำหนด

## สิ่งที่ ER ยังไม่ครอบคลุมฟังก์ชันใน Figma ทั้งหมด

ส่วนนี้เป็นรายการให้ตัดสินใจ ไม่ได้เพิ่มลง SQL โดยพลการ:

1. Driver เริ่มงาน/เช็กอินผ่านจุดจอด: ER นี้ไม่มีตารางบันทึกเวลาที่รถผ่านแต่ละจุด ข้อเสนอคือตาราง `trip_stop_events` อ้าง `BUS_TRIP_ROUNDS` กับ `BUS_ROUTE_STOPS` และเพิ่มเวลาเริ่ม/จบงานในรอบรถ เมื่อผู้ใช้อนุมัติ
2. หน้ารถใน Figma มีรุ่น/ยี่ห้อ ปี และสถานะซ่อมบำรุง แต่ ER รถมีเพียงรหัส ทะเบียน ประเภท จำนวนที่นั่ง ต้องตกลงว่าจะขยายตารางหรือปรับหน้าจอ
3. Account มีชื่อในรายการต้นเอกสารหน้า 1 แต่ไม่มีโครงสร้างใน ER หน้า 4–5 จึงยังไม่สร้างตาราง Account เพิ่ม
4. ตะกร้ารอยืนยันยังไม่จำเป็นต้องเป็นการจองจริง อาจเก็บชั่วคราวใน Client ถ้าต้องการข้ามเครื่อง/กลับมาแล้วรายการยังอยู่ ต้องตกลงการเก็บ draft เพิ่ม
5. การเช็กอินผู้โดยสาร QR/เวลาเช็กอินอยู่ในตั๋ว แต่การเช็กอินรถตามจุดเป็นคนละข้อมูลกัน

## กฎที่ต้องทำใน Server/ธุรกรรม หลังอนุมัติ

FK พื้นฐานยังไม่ตรวจทุกเงื่อนไขธุรกิจ: คนขับต้องมีตำแหน่งคนขับ, รถและคนขับห้ามมีรอบเวลาทับ, จุดขึ้นและลงต้องอยู่บนเส้นทางของรอบรถและเรียงถูก, เลขที่นั่งต้องมีจริง, จำนวนที่จองต้องไม่เกินข้อกำหนด, ต้องจองก่อนเวลาที่กำหนด, เวลารวมเส้นทางและเวลารับต้องตรงกับจุดจอด, และสถานะการจองต้องสอดคล้องกับตั๋ว

ต้องทำการยืนยันหลายรายการและยกเลิกด้วย transaction รวมถึงจัดการกรณีคนสองคนกดที่นั่งเดียวกันพร้อมกัน ส่วน username ต้องกำหนดว่าจะสนใจตัวพิมพ์ใหญ่/เล็กหรือไม่

ร่างใช้เวลา Asia/Bangkok แบบไม่มี timezone อยู่ในแต่ละ TIMESTAMP ตอนทำ Server ต้องกำหนด timezone ของ DB session และรูปแบบ API ให้ตรงกัน

## ให้ตรวจก่อนเริ่มทำจริง

- ภาพหน้าจอยืนยันว่าใช้ Oracle แล้ว ยังต้องทราบเวอร์ชันถ้าเป็นไปได้
- อนุมัติรายการ 13 ตารางและ FK ในตารางสรุป
- เลือก PK ของตั๋ว: PK คู่ `(booking_id, ticket_no)` ตาม Partial Key หรือ PK เดี่ยวไม่ซ้ำทั้งระบบ
- ตรวจความหมายหนึ่งการจองต่อหนึ่งรอบรถ, เวลาเดินทางเป็นเวลารับที่จุดขึ้น, และกันที่นั่งตลอดรอบ
- ตัดสินใจส่วนขยายเพื่อให้ฟังก์ชันเว็บครบเหมือน Figma โดยเฉพาะเช็กอินตามจุดและข้อมูลรถ
- ก่อนสร้าง Client/Server ขอเปิดดูโครงโปรเจกต์เดิมหรือไฟล์ที่เคยใช้ เพื่อเลือกเทคโนโลยี Server ให้ตรงกับที่ผู้ใช้เรียนมา

หลังผู้ใช้ยืนยันจึงปรับ SQL เป็นฉบับพร้อมใช้ วางแผนการรัน และเริ่มต่อ Client/Server ตามขอบเขตที่อนุมัติ

การตรวจร่างนี้เป็นการตรวจโครงสร้างไฟล์และความสัมพันธ์กับ ER เท่านั้น **ยังไม่ผ่านการรันบน Oracle จริง**
